# Avito.Kitchen

MVP сервиса для заказа еды из ресторанов.

## О проекте

Проект состоит из двух приложений:

- `kitchen-api` — основной API и бизнес-логика приложения;
- `restaurant-mock` — отдельный HTTP-сервис, который имитирует внешнее API ресторана;
- PostgreSQL — постоянное хранилище данных основного сервиса.

Основной поток обработки:

```text
Клиент
   |
   v
Handler -> Service -> Repository -> PostgreSQL
                |
                +-> RestaurantClient -> Restaurant API
```

Подробные схемы находятся в `docs/c4.md`, `docs/cjm.md` и `docs/architecture.md`.

## Что умеет приложение

Основные пользовательские сценарии:

1. Просмотр списка ресторанов.
2. Просмотр меню ресторана.
3. Добавление блюда в корзину.
4. Изменение количества блюда.
5. Удаление блюда из корзины.
6. Оформление заказа.
7. Просмотр списка заказов.
8. Просмотр конкретного заказа.
9. Повторное оформление заказа с защитой от дублирования через `Idempotency-Key`.

## Запуск

Для запуска всего проекта:

```bash
docker compose up --build
```

После запуска:

```text
Основной API:       http://localhost:8080
Restaurant Mock:    http://localhost:8081
PostgreSQL:         localhost:5433
```

Проверить работоспособность основного API:

```bash
curl http://localhost:8080/health
```

Миграция базы данных выполняется основным приложением при старте, поэтому отдельный контейнер для миграций не требуется.

## API

Полное описание API находится в:

```text
docs/openapi.yaml
```

Основные маршруты:

```text
GET    /health
GET    /api/v1/restaurants
GET    /api/v1/restaurants/{id}
GET    /api/v1/restaurants/{id}/menu

GET    /api/v1/cart
POST   /api/v1/cart/items
PATCH  /api/v1/cart/items/{id}
DELETE /api/v1/cart/items/{id}

POST   /api/v1/orders
GET    /api/v1/orders
GET    /api/v1/orders/{id}
```

Для работы с корзиной и заказами используется заголовок:

```http
X-Session-ID: test-user-1
```

При создании заказа можно передать:

```http
Idempotency-Key: order-001
```

Повторный запрос с тем же ключом не создаст второй заказ.

## Основные решения

### Одна корзина — один ресторан

В корзине можно хранить блюда только одного ресторана.

Это позволяет не усложнять оформление заказа: один заказ всегда отправляется одному ресторану.

### Снимок цены

В `order_items` сохраняются название и цена блюда на момент оформления.

Поэтому если позже цена блюда изменится в `menu_items`, уже созданный заказ не изменится.

### Идемпотентность

`Idempotency-Key` используется вместе с `X-Session-ID`.

Если пользователь повторно отправит тот же запрос:

```text
Первый запрос
    |
    +-> создаётся заказ №1

Повторный запрос с тем же ключом
    |
    +-> возвращается заказ №1
```

Повторно отправлять заказ в ресторан не требуется.

### Взаимодействие с рестораном

Основной сервис синхронно обращается к `restaurant-mock` по HTTP.

Если ресторан временно недоступен, HTTP-клиент выполняет повторные попытки с увеличивающейся задержкой.

### Транзакции и конкурентный доступ

Создание заказа и изменение корзины выполняются с учётом транзакционных границ PostgreSQL.

Для дальнейшего усиления checkout можно добавить блокировку корзины через `SELECT ... FOR UPDATE` и outbox-паттерн.

## Тестовый сервис ресторана

`restaurant-mock` — отдельный HTTP-сервис, который запускается вместе с основным API через Docker Compose.

Он поддерживает:

```text
GET   /health
GET   /api/v1/menu
POST  /api/v1/orders
GET   /api/v1/orders/{id}
PATCH /api/v1/orders/{id}/status
```

Статусы заказа:

```text
accepted
preparing
ready
delivered
cancelled
```

Заказ в тестовом сервисе идемпотентен по идентификатору заказа основного API, поэтому повторные запросы не создают дубликаты.

Для проверки ошибок и задержек можно использовать:

```text
MOCK_FAIL_COUNT
MOCK_FAIL_STATUS
MOCK_DELAY_MS
```

Например, `MOCK_FAIL_COUNT=2` заставит первые два запроса создания заказа завершиться временной ошибкой.

## Повторные запросы и ошибки

HTTP-клиент ресторана повторяет временные ошибки и сетевые ошибки.

Всего выполняется первоначальный запрос и до трёх повторных попыток.

Используется exponential backoff.

Повторные запросы не выполняются для:

- HTTP 4xx;
- отменённого контекста;
- истёкшего контекста.

Каждая попытка использует один и тот же ключ идемпотентности.

Если ресторан так и не смог принять заказ:

```text
локальный заказ -> failed
HTTP-ответ      -> 502 Bad Gateway
```

Ошибки валидации возвращаются как `400`, внутренние ошибки хранения — как `500`.

## Проверка

Запустить тесты:

```bash
go mod tidy
go test ./...
```

Проверить форматирование:

```bash
gofmt -l .
```

Запустить статический анализ:

```bash
golangci-lint run
```

Тестами покрыты:

- идемпотентность создания заказа;
- пустая корзина;
- повторные запросы клиента ресторана;
- ошибки `4xx`, которые не должны повторяться;
- таймауты и отмена контекста;
- проверка статусов ресторана;
- допустимые переходы между статусами.

## Структура проекта

```text
cmd/
  kitchen/       запуск основного API
  restaurant/    запуск тестового сервиса ресторана

internal/
  client/        HTTP-клиент ресторана
  config/        конфигурация
  handler/       HTTP-обработчики
  model/         модели данных
  repository/    работа с PostgreSQL
  service/       бизнес-логика
  storage/       подключение к БД и миграции

migrations/      SQL-миграции
docs/            OpenAPI, архитектура и диаграммы
```
